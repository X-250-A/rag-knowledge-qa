## 近日完成：

- ##### rerank重排序的上线：
  
  - 对单例懒加载的认识
    
    - **单例：** 进程对象唯一，**懒加载：** 不随程序运行加载，除非用到
    
    - 以下为示例：
      
      ```
      _model = None
      
      def _get_model():
          global _model
          if _model is None:
              _model = CrossEncoder(MODEL_NAME)
          return _model
      ```
      
      - **_model：** 声明的全局变量，利用py的语言特性实现“单例”效果。下划线"_"代表该变量模块私有 
      
      - **global：** 修改全局变量的必要声明
    
    - 优势：
      
      - 避免每次运行程序都加载对应模型，徒增内存开销。如本项目中，使用单例懒加载处理reranker模型，能够避免每次运行程序都花费10s和2.3G空间。
    
    - 劣势：
      
      - 在多线程操作使模型被多次加载，容易浪费内存，甚至内存互相覆盖。这是单例懒加载的经典缺陷
    
    - 完善：
      
      - 对于单例懒加载的劣势，可以为加载过程“加锁”，加互斥锁，使单例懒加载的单if检查升级为双重检查。至于为什么加互斥锁，目前没有基础知识储备，就不展开了。

- ##### CRUD层的优化：
  
  - 先前各个CRUD函数中都包含commit + refresh流程，依赖项get_db也同步commit + rollback配套，导致CRUD边界模糊。同时破坏了事务一致性。这个据glm所说，叫：**边界上收**  。
  - 现在删除各个CRUD的commit + refresh，让边界清晰，事务可回滚。职责更明确，溯源更容易。

- ##### 项目可观测性的增强：
  
  - 原先的logging_config，采用BasicConfig实例化日志记录器，实现了请求级日志记录。
    
    - 但是，缺点是日志无轮转，容易单文件无限膨胀，同时缺乏业务级日志，难以真正溯源。
    
    - 这段时间改动了logging配置，首先通过模块级单例configured + if检查 + 函数内部 configured = True实现幂等操作。（双重保险）
      
      - 幂等，简单说，就是多次操作等同于一次操作，可以防函数重复调用，避免日志内容重复等场景。
    
    - 同时，放弃BasicConfig类，改用能更实现app.log日志文件轮转的RotatingFileHandler类。配置路径，maxBytps，encoding等参数
    
    - 手动挂载file_handler和console_handler等日志内容出口。
  
  - 手写crud_log装饰器，统一log出口格式与出口文件
    
    - 装饰器，本质是py的高级函数用法的拓展（py可返回函数），这里讲需要传参的情形。
      
      - 最外层，负责闭包捕获外界参数，让py自动将参数塞入内部
      
      - 中层decorate，负责接收一个函数
      
      - 最内层@functool + async def，实现真实业务，最后返回值
    
    - 调用时，在装饰器下定义函数，不仅可以实现原本的功能，还可以实现调用器工厂内部定义的函数功能，例如router下的auth路由
